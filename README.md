# Tessera

A deterministic, single-player weighted-sum grid puzzle.

Place the digits 1–N² into an N×N grid — each digit used exactly once — so that every row and every column hits its target. The twist: position matters. Each slot carries a weight, and a line's score is the sum of each digit multiplied by its slot's weight.

```
col weights →    ×1    ×2    ×3
                ┌─────┬─────┬─────┐
row 1  ×1  │  7  │  2  │  4  │  = 23  ✓
                ├─────┼─────┼─────┤
row 2  ×2  │  1  │  9  │  3  │  = 28  ✓
                ├─────┼─────┼─────┤
row 3  ×3  │  6  │  5  │  8  │  = 40  ✓
                └─────┴─────┴─────┘
                  = 27  = 35  = 34
                   ✓     ✓     ✓
```

Swapping any two digits changes at least one line's score — so order is everything.

## How the puzzle works

The combine function is:

```
lineValue(digits, weights) = Σ digits[i] × weights[i]
```

Default weights are `[1, 2, …, N]` for both rows and columns. With a 3×3 grid:

- **Row score** = digit at col 0 × 1 + digit at col 1 × 2 + digit at col 2 × 3
- **Col score** = digit at row 0 × 1 + digit at row 1 × 2 + digit at row 2 × 3

Every puzzle has exactly one valid arrangement. The generator verifies this before presenting the puzzle to the player.

### What gives math-savvy players an edge

- The digits always sum to N²(N²+1)/2 — a fixed total that constrains the targets.
- Heavy positions (high weight) strongly prefer large or small digits. Placing 9 in the bottom-right corner of a 3×3 grid contributes 9×3 = 27 to *both* its row and its column simultaneously.
- Row and column targets are not independent — they share the same digit pool.

These observations are not shown in the main UI; they surface only through the hint system.

## Architecture

The combine function (`core/src/combine.ts`) is the single source of truth for the weighted-sum formula. Every component that evaluates a line — the solver, the generator, the UI feedback, the reveal panel, and the future Rust on-chain verifier — calls `lineValue` from that file. Replacing the formula (e.g., with a 2×2 matrix product) requires editing only that one file.

### Serialization

| Cell type | Size | Layout |
|-----------|------|--------|
| Tile cell | 9 bytes | `puzzle_id[8] \| value[1]` |
| Puzzle cell | 9 + 6n bytes | `puzzle_id[8] \| n[1] \| rowWeights[n] \| colWeights[n] \| rowTargets[n×2 LE] \| colTargets[n×2 LE]` |

The byte layout is designed to be consumed directly by a CKB Rust type script.

### Solver performance (current)

| N | Mean solve time | Max solve time | Max nodes |
|---|----------------|---------------|-----------|
| 2 | < 1 ms | < 2 ms | ~8 |
| 3 | ~1 ms | ~3 ms | ~750 |
| 4 | ~1.7 s | ~5.6 s | ~8 M |

N=4 meets the 5 s mean target. The solver uses a backtracking algorithm with
row-completion pruning and per-column forward checking via 32-bit bitmasks.
See [`core/SOLVER.md`](core/SOLVER.md) for a full account of the algorithm,
the three implementation iterations, and the benchmark progression.

## Future: CKB on-chain verifier

The planned Rust type script will verify a solve transaction:

- **Inputs**: one puzzle cell + N² tile cells in row-major order
- **Output**: one trophy cell (`puzzle_id` + solver's lock hash)
- **Checks**: tile count, distinct values in 1..N², every row and column weighted sum against the puzzle cell targets

`test-vectors/vectors.json` (generated by `core`) provides cross-language test coverage so the TypeScript and Rust implementations must agree.

CKB work does not begin until playtesting sign-off. See `PLAYTESTING.md` (created in Phase 5).
